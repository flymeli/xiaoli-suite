## 1. 产品是什么、面向谁、定位与核心价值

校哩是面向**经核验的在校大学生**的校园生活与兴趣社区。它提供图文、纯文字与基础短视频分享，以及同校讨论和受权限约束的跨校发现。产品价值是帮助学生找到与自己校园相关的信息，并得到真实同学的回应。身份认证是准入基础；认证徽章不代表对用户言行或交易信用的担保。（产品规格开篇、§1.2、§3.3）

本轮已确认的最高优先级要求为 U01 至 U06（产品规格 §1.1）：

| 编号 | 已确认要求 | 约束 |
|---|---|---|
| U01 | 校园版内容与社交社区 | 不能演变成泛娱乐流量平台 |
| U02 | 图文、视频、评论等基础能力 | 首期必须包含可用的图文和基础短视频链路 |
| U03 | 必须经过学信网认证，严格控制学生人群 | 学生证 OCR、学校邮箱、运营邀请均不能独立授予正式学生权限 |
| U04 | 大学身份标签与各自校园圈子 | 学校归属来自核验结果；认证后获得本校社区成员资格 |
| U05 | 广场能够发现各校园相关话题 | 跨校发现成立，但必须遵守作者选择的可见范围 |
| U06 | 集市商城能力未来扩展 | 首期不进入商品订单、支付、退款和商家履约 |

核心用户与首次价值体验（§3.3）：新入校学生查宿舍、食堂、选课与校园规则；日常浏览学生看同校动态和有用讨论；表达与创作学生分享后被同校同学看见并得到回应；社团及兴趣组织者以核验学生个人身份组织讨论，社团徽章不能由学生认证自动推导。

差异化假设（§3.2，待验证）：对照小红书、掌上大学、微信/QQ 群与校园墙、学校公众号，校哩要用更高的本校信息命中率和更稳定的回应，证明学生愿意为明确的校园价值完成认证。仅提高注册门槛不足以构成迁移理由。全国高等教育在学规模只作背景，不能直接当可服务人数或收入预测（§3.1，[R08]）。

可行性判断（§1.3）：用户价值和产品闭环值得验证；技术实现有条件可实施，前提是合法认证路径及本人绑定通过验证；运营需要独立人力；商业模式尚待实证；历史九周排期不应继承。项目建议进入「前置验证和试点准备」。若认证授权或本人绑定无法解决，应暂停正式学生社区上线，不能通过降低认证标准绕过 U03。

建议首期选择两所具备运营资源的学校做封闭试点。底部五个入口是「校园、广场、发布、消息、我的」。认证后自动归属本校内容空间；即时聊天群由成员主动加入，放在后续版本。图文与视频共同进入内容流，视频提供独立详情播放，不另建首期全屏视频主入口。（§1.2）

正式商标与应用名称可用性另行确认。原技术文档文件名用「校哩」，正文曾用「墙墙」；产品规格已统一使用「校哩」（§2.1）。

## 2. 模块与功能清单、关键用户流程

### 2.1 范围分期

产品规格 §16.1 与技术文档现行第 1.5、第 3 章口径一致：

| 阶段 | 交付范围 | 进入下一阶段的条件 |
|---|---|---|
| G0 前置验证 | 用户研究、准入决策、认证授权与本人绑定、关键 SDK 验证、核心原型、预算 | 关键依赖有证据，产品与权限基线冻结 |
| P0 封闭试点 | 账号与认证、校园与广场、图文短视频、评论赞藏关注、搜索话题、消息与受控私信、治理后台、数据权利 | 核心旅程通过，S0/S1 清零，值班与试点供给准备好 |
| P1 留存与关系增强 | 本校兴趣或社团群、创作者反馈、必要体验提升、按验证结果改进推荐 | 校园密度与留存稳定，新增治理与成本可承担 |
| 商业实验版本 | 有标识赞助或有限广告，之后再评估创作者激励 | 广告准入、归因、结算、合同、税务及反作弊完成验证 |
| P2 集市与交易 | 信息发布验证后再建设订单、支付和售后 | 交易需求和服务能力成立，独立产品及合规评审完成 |

建议延期、首期不出现入口的能力（产品规格 §2.3、§7.1、附录 A 文末；技术文档 §3.3）：现金分账、邀请解锁收益、代理自动分成、钱包与提现、完整广告系统、复杂保量推荐、完整群聊、29 个频道全量启动、三端同时承诺、匿名树洞、独立视频 Tab、直播、兴趣选择步骤。集市订单与履约按 U06 后置。后置功能在未来版本中保留业务位置，但首期不显示不可用的钱包、收益或商城入口。

- 社交：RQ-S01 至 RQ-S05（私信请求、已建立会话、屏蔽举报、消息通知、隐私与通知设置）；RQ-S06 为本校群，属 P1

### 2.3 关键产品规则（摘要）

**准入四条件必须同时成立**（§5.1—§5.2）：学信网依据有效、申请人与报告主体一致、当前在读合格、学校匹配。不采集学信网账号密码，不在 App 内模拟官方登录，不把 OCR、邮箱后缀、姓名相同或验证码首次使用作为单独通过依据。P0 只有两条待核实路径：取得合法授权的核验服务，或用途与流程确认后的受控人工核验。两者都无法形成可靠闭环时，正式学生社区不得上线。

账号、学生资格、业务角色必须分离（§4.3）。学校开通是四态（筹备、封闭试点、开放、暂停），社区权限只有两套；不能用一个 `school.enabled` 代替（§4.2、§6.4）。未登录或已登录未认证用户不接触学生 UGC。认证有效但学校未开通（或未进入试点名单）可浏览全站学生可见内容并互动、使用受控私信，但不可发布任何新作品。

可见范围首期只有「本校可见 SCHOOL」和「全站学生可见 ALL_VERIFIED」；新作品默认本校，须用户主动选择才能扩大。关注不改变可见范围。所有访问路径（Feed、搜索、话题、主页、收藏、通知、分享、媒体地址）使用同一规则；权限变更后下一请求拒绝，已签发媒体链接最多 60 秒残余窗口（§6.3—§6.4、§15.3）。

审核是「完成后可见」：自动筛查返回可公开后才对他人可见；高风险、不确定或有效举报进入人工，结论前不公开；筛查超时或服务不可用时保持审核中，不自动公开（§7.3，审计项 A10）。

私信：接受前只能发一条文字请求（建议最多 200 字，无图、无视频、无可点击外链）；拒绝后冷却 7 天；待处理 7 天过期后可再发一条；接受后文字和图片先审后达；互关不等于接受；资格失效后 App 内不提供只读会话。校园成员资格自动建立，不等于自动加入 IM 群（§8.2、§8.5）。

首期建议参数（须 G0 用真实样本验证后冻结，§7.1）：图文 1 至 9 张、单张不超过 20MB；标题最多 30 字、正文最多 2000 字；纯文字至少 2 个有效字符；短视频一篇一个、3 至 180 秒、原文件不超过 200MB；评论最多 500 字、两层展示；每篇最多 3 个已有话题；本机草稿最多 20 条；新账号每日最多 5 篇。首期六类频道：校园生活、学习成长、求助问答、社团活动、兴趣同好、新生指南。

## 3. 技术架构、技术栈与成熟度

### 3.1 现行建设依据

技术文档开头写明：建设依据是第 1 章、第 3 章、第 4.1 节，以及后文标有「现行规则」的段落。标有「历史笔记，不得实现」的章节保留原文供对照，不能把其中的接口、表字段、广告位或工期抄进新代码。产品规格高于本文。DEC01 至 DEC10、PC01 至 PC08 仍未批准。具体路径、字段和错误码在 DEC09 之前不冻结。

现行技术方向（技术文档 §1.2，与产品规格 §15.1 一致）：

- 架构沿用**模块化单体**和**托管媒体**，减少早期跨服务协调。
- **Flutter 与 Go 是候选继承技术**，不是已经签下的供应商合同。端侧、SDK 版本和开发者熟练度，在 G0 技术决策记录里锁定。
- 腾讯云一类 PaaS 只是托管媒体、即时消息和内容安全的**候选**，须先完成 PC03、PC04、PC05 的证据。
- 业务域分成账号、学生资格、学校成员、内容媒体、互动、发现搜索、消息、治理、运营和数据。交易与账务只留边界，不提前建钱包、订单或分账。
- 权限在服务端集中执行。客户端上报的学校、资格、可见范围、审核结论和处罚都不被信任。
- 先做 iOS 与 Android 的一致核心体验。HarmonyOS 单独验证关键 SDK 后再估算，DEC03 未批准，不与双端同步交付。H5 可以做原型，不等于商店里的 App。

现行工期（技术文档 §1.5、§18 章首段「现行规则」；产品规格 §16.2—§16.3）：不继承九周、四人外包或三端同时交付。一人主导并使用 AI 辅助时，P0 双端按 100 至 150 个有效工程人日估算，参考窗口约 27 至 54 周；若配置 1 名移动端、2 名后端或全栈、1 名独立 QA 并有产品与运营支持，到可试点版本约 10 至 16 周。这是初始估算，不是完工承诺。实现时先打通账号、认证、校内发帖、审核、浏览、评论这一条闭环，再扩展视频、跨校和消息。

性能建议目标（产品规格 §15.4、技术文档 §1.5）：核心 API P95 不超过 500 毫秒；首页首屏 P95 不超过 2.5 秒（指定中档机、10Mbps、100ms RTT、冷启动）；视频首帧 P95 不超过 2 秒；旧媒体授权残余不超过 60 秒；试点月度可用性 99.5%；关键业务 RPO 不超过 1 小时、RTO 不超过 4 小时。这些不是已经达到的成绩，也不继承旧文中的冷启动 2 秒、首帧 500 毫秒、20 万注册或 6 万日活。

### 3.2 历史技术栈（对照用，不得直接当成已批准选型）

技术文档第 2 章整章标注「历史笔记，不得实现（2026-11-06）」。其中的版本、容量和广告 SDK 不是现行承诺，但反映了原文曾准备采用的候选组合，G0 技术决策时需要逐项重新确认：

| 层级 | 历史稿中的选择 | 文档中的版本或要点 |
|---|---|---|
| 客户端 | Flutter + GetX + dio | 曾锁 3.22.x，但播放器 SDK 要求 Flutter ≥3.27.4 / Dart ≥3.6.2 / Xcode ≥16 / iOS ≥13，二者冲突（历史风险 R-02） |
| 后台 | gin-vue-admin（Go + Vue） | 现行规则：只是候选框架（§5 章首段） |
| 后端 | Gin + GORM 手写模型 | Go 1.21+ |
| 数据库 | MySQL 8.0 主从 | 禁止单机 |
| 缓存 / 队列 | Redis 6.x 主从 + Sentinel；P0 用 Redis Stream | 禁止单机 |
| 搜索 | MySQL FULLTEXT（ngram，二元） | P0 不引入 Elasticsearch |
| 对象存储与点播 | 腾讯云 COS + VOD + CDN | 直传签名由服务端下发 |
| IM | `tencent_cloud_chat_uikit` | 旧包 `tim_ui_kit` 已停更 |
| 播放器 | 腾讯云视立方 SuperPlayer | 不使用已停更的 fijkplayer；鸿蒙端未验证（历史风险 R-03） |
| 推送 / 短信 / 审核 / 日志 / 监控 | 腾讯云 TPNS、SMS、内容安全、CLS、云监控、Bugly | 「能用腾讯云就优先用腾讯云」是历史底座策略 |

## 4. 设计系统要点

来源：UIUX 手册 §1—§3、§9，以及 `xiaoli_design_tokens_v1.json`（status：`v1_suggested_baseline`，修订 2026-11-06）。视觉定位：让学生快速理解三件事——这里属于哪所学校，这条内容谁能看到，下一步可以做什么。浅色为默认主题，深色跟随系统。活力来自学生内容，大面积保持雾白，蓝色集中用于主动作、当前选择、链接和进度。

### 4.2 尺寸、圆角、图标与底栏

- 基础间距单位 4；页面边距 16；主画板逻辑尺寸 390×844，另检 360×800 与 430×932。

- 已选筛选标签不能只靠浅底，须同时使用主色文字、字重 600 和 2 逻辑单位主色描边。
- 图标：Lucide 线性，24×24 视框、2 线宽。底栏映射：校园 `school`、广场 `compass`、发布 `plus`、消息 `message-circle`、我的 `user-round`。Logo 确定前，原型以「校哩」文字标识呈现，不用学校或盾牌图标临时代替，也不把 SF Symbols 当 App 图标。
- 底部五入口内容区至少 64，另加运行时安全区。发布是创作动作：视觉 40 的蓝色容器，下方间距 4 再排「发布」文字。未认证用户进入认证服务区，不展示大量不可用的空内容入口。
- 校园首页采用单列混合内容流（时间倒序）；广场采用双列探索流，系统文字放大约 130% 起改单列。

认证状态组件 IdentityBadge 必须覆盖主文完整状态文案（未开始、处理中、需要补充、人工确认中、已认证、需续验、未通过、已失效、已暂停等），不能收成「已认证 / 待审核 / 未通过」三枚芯片。视觉速览图若仍画出 56 高底栏或只有三枚状态芯片，以手册和 JSON 为准（手册 §9.1）。
