## 2. 分项说明

### 2.1 DEC01 年龄范围

**主文原建议（§4.1、§19）：** P0 先以 18 岁及以上做有限试点，是为了匹配早期治理能力，不是法律规定，也不能把未满 18 岁的真实大学生说成身份不真实。若首期接纳未成年大学生，必须在开放前完成可信年龄分层、适龄内容、陌生人私信限制、投诉与监护相关机制，并重新估算工作量（[R15]）。年龄证据只来自核验回执中的出生日期或年龄结论；资料里的展示生日不改变权限。核验路径不能返回可靠年龄时，不得改用自填生日放行。

**本次决定：** 不限年龄。只要能完成学信网认证（见 DEC10），不把 18 岁作为首期门槛。

**分层状态：** 产品方向已确认。由此引入的未成年人保护和必要年龄分层**必须另行设计**，不能暗中把 18 岁门槛写回认证失败码或后台默认值。

**对主文 / 原型 / 开发的约束：**

- 主文 §4.1、§4.2 权限矩阵中的「满足年龄和账号规则」、§19 DEC01 建议，以及认证失败「未达建议年龄」的独立原因码，都与本次方向冲突，待修订主文；在修订前，开发与原型按本次记录，不按 18 岁默认挡人。
- 现有 OpenDesign 认证结果、帮助和资料页还没有未成年人模式、监护或私信加严状态（见 01 文档）。完善原型时要为这些状态留位，但字段不能先画死。
- 开发不得用资料生日、自行填写的年龄或「看起来已成年」放行。核验回执若暂时给不出可靠年龄，分层保护无法按真实年龄启用，应标为风险，而不是改回 18 岁一刀切。

**仍未完成：** 年龄分层档位、适龄内容与推荐限制、未成年私信与陌生人请求规则、投诉与监护机制、终端未成年人模式与 App 内规则如何衔接、工作量重估。这些是开放前的设计与合规任务，不是可选项。

### 2.2 DEC02 学籍范围

**主文原建议（§4.1、§4.4、§19）：** 试点先面向可完成学信网在读学籍核验的普通高校本专科及研究生；全日制为首期建议主范围。非全日制、成人教育、开放教育等是否纳入由 DEC02 明确，**不根据「学信网查得到」自动放开**。学信网学籍查询范围不含自考，且包含部分已离校档案；拥有学信网记录、有学历、已经录取和当前符合在读资格，是不同判断。海外学校及其他无法使用同一依据的人群不在本期认证承诺内。休学、保留学籍、退学、未知状态，主文建议首期仅「在读且满足准入规则」生效，其他进入待核或不符合。

**本次决定：** 学籍不限，都可支持。结合 DEC01、DEC10，前提仍是「必须能学信网认证」。

**分层状态：** 产品方向已确认的是：**不要把可支持的培养类型锁死在普通全日制本专科及研究生**。例如非全日制、成人教育、开放教育等，只要能走通经确认的学信网核验路径，系统设计就要能支持，而不是先在代码里写死拒绝。

**不得自行扩大的边界（有歧义处已标明）：**

- **不能**把「学籍不限都可支持」理解成：所有毕业、结业、肄业身份自动获得学生社区权。主文已区分「有学信网记录 / 有学历 / 已录取 / 当前在读资格」。已离校档案能被查到，不等于当前有权使用在校学生社区。
- **自考：** 主文依据 [R01] 写明学信网学籍查询范围不含自考。本次决定没有单独宣布把自考纳入。若自考只有学历或非学籍类依据，是否支持、用哪一种报告，标为**边界待细化**，不能在实现里默认通过。
- **休学、保留学籍、退学、未知状态：** 用户未逐项点名。本次记录为：系统要能接收并区分这些状态，但**哪些状态授予社区权、哪些只进入待核或不符合**，仍待细化。在细化前，开发不得把上述状态一律放行，也不得继续用「仅全日制」做死拒绝。
- **录取未注册、报告过期：** 仍按主文 §4.4：录取通知书不替代正式核验；报告过期引导更新，不能直接标造假。
- **海外学校及无法使用同一学信网依据的人群：** 本次未纳入，维持主文「不在本期认证承诺内」，除非以后另作决定。
- 学校归属仍来自核验结果，不能由用户自填学校取得正式学生权限（U04、§5.2）。

**对主文 / 原型 / 开发的约束：** 主文 §4.1、§19 的「全日制为主」需后续修订。认证失败原因、学校主数据和帮助文案要改成按核验状态判断，而不是按培养类型一刀切。原型 `authSubmit`、`authResult` 仍是占位，等 DEC10 / PC01 和本项状态白名单一起冻结字段。

### 2.3 DEC03 首发端

**主文原建议：** iOS 与 Android 核心一致，鸿蒙保留为端侧扩展，在真实设备完成关键 SDK 验证后独立估算。

**本次决定：** 按建议先做 iOS 与 Android，暂不鸿蒙。

**分层状态：** 产品方向已确认，与主文建议一致。PC07（跨端构建、最低系统、关键 SDK 真机验证）仍待验证。一人路线下若先做一个客户端做封闭试点，属于主文已允许的缩短周期办法（§16.2），如要采用需另记一笔，本次未要求只做单端。

### 2.4 DEC04 团队路线

**主文原建议：** 一人加 AI 作为重点预算路线；独立产品设计、QA、人工审核、校园运营和商务办理另计。工程量级按 100 至 150 个有效工程人日做初始估算，不预设 AI 固定提效倍数。该路线仍需要外部或兼职设计、独立测试和运营审核支持；不能让开发者在编码同时承担无备份的全天候审核。

**本次决定：** 以一人加 AI 为主。

**分层状态：** 产品方向已确认。工期、兼职支持和审核值班仍未回填。历史技术文档中的九周外包表不得执行，也不能把 27 至 54 周参考窗口写成承诺。人工认证兜底（DEC10）会额外占用审核产能，与「一人编码」不是同一件事。

### 2.5 DEC05 首期商业化

**主文原建议：** 现金、邀请解锁、代理自动分成与广告平台后置。

**本次决定：** 首期先不做商业化相关，后续再补充。

**分层状态：** 产品方向已确认，与主文建议一致。P0 不显示不可用的钱包、收益或商城入口；不提前集成广告、支付等非必要 SDK（§10.2）。后续若做商业实验，需另立决策，并完成账务、合同、税务和反作弊验证（§16.1）。当前 OpenDesign 稿没有这些入口，应保持，不要从墙墙旧稿倒灌回来（01 文档第 5、7 节）。

### 2.6 DEC06 圈子与群

**主文原建议：** 校级社区自动归属，IM 群放 P1，自愿加入。

**本次决定：** 首版先做社区和私信，群聊后置。

**分层状态：** 产品方向已确认，与主文建议一致。F01 群聊提示词不得贴进 P0 项目。消息和校园页不要加群入口或「即将开放」占位。PC05（IM 发送前控制）仍是私信能否从示意变成可开发规格的验证项，与群聊后置不是同一件事。

### 2.7 DEC07 内容可见

**主文原建议（§4.2、§6.3、§19）：** 新作品默认本校可见；用户主动选择后才能扩展至全站学生。「全站学生可见」中的全站，指平台内已有效认证、满足账号规则的学生，**不等于互联网公开**。首期不做互联网公开、仅互关可见或复杂自选名单。

**本次决定：** 按建议，默认本校，可选全站公开。

**口径约束：** 这里的「全站公开」在实现、文案和帮助里，必须写成并对齐为**全站已认证学生可见（ALL_VERIFIED）**。不能把这句话扩大成互联网匿名可见，也不能让未登录或未认证账号通过分享链接、搜索、缩略图或媒体地址看到学生 UGC（§6.4、附录 A）。发布前仍须用文字展示范围，并在扩大到全站学生时二次确认。

**分层状态：** 产品方向已确认。当前原型发布设置已有「仅本校 / 全站学生」和确认扩大范围，方向是对的；分享、通知深链和媒体地址的同一权限仍不完整（01 文档），属于实现缺口，不是方向未定。

### 2.8 DEC08 首校与预算

**主文原建议（§13.1、§19）：** 先选两所可以持续覆盖的学校；开通状态为筹备、封闭试点、开放、暂停。没有运营负责人和审核保障的学校不直接放开自由发布。按无收入安排运营跑道。

**本次决定：** 试点按建议进行，打算现在四川的学校试点；代码上不限制只可以两校；学校开通配置化。

**分层状态：** 产品方向已确认。具体学校名单、运营联系人、种子供给、审核值班和资金跑道仍未定，不能把「四川两校」写成已经锁定的上线名单。

**对开发的约束：** 学校开通必须配置化，落成主文四态，不能用一个 `enabled` 布尔值代替，也不能把学校数量写死为 2。封闭试点是「已开通」的名单限制，不另造一种可见范围（§4.2、§6.4）。未开校学生可按主文浏览全站可见内容、暂不可发布。

### 2.9 DEC09 复核与数据参数

**主文原建议（§5.4、§10.2、§10.3、§19）：** 资格最长 180 天复核一次，提前 14 天提醒；这是校哩建议运营参数，不是官方要求。官方报告验证期与平台资格复核周期是两件事。数据按类别设置清理期限，G0 完成必要性和技术实现评估后统一配置；建议值不是法定期限。

**本次决定：** 资格复核暂定一年一次；资格不是永久权限，可以因撤销、毕业或状态变更提前失效或收回。各类数据按分类评估。

**分层状态：** 产品方向已确认，但一年是**暂定参数**，分类保留期限仍待评估，不能写成已批准政策，也不能写进对外承诺。原型 `myIdentity` 若仍写「下次复核 2027 年 6 月」之类示例，只能当示意，须在文案上标明未冻结。

**需要一并保留的规则：** 预计毕业或学籍状态变化可提前触发复核或收权，不必等到满一年。报告本身若有更短可验证期限，处理时仍须确认报告仍有效。平台无法保证两次核验之间学籍永不变化，徽章应反映核验时间范围，并保留举报复核和风险触发。备份恢复不得复活已删除数据（§10.2、§10.3）。认证材料与长期资格凭据分开，短期清理建议仍待分类评估后冻结。

**与主文的冲突：** 180 天建议改为暂定 365 天（一年）。数据分类评估的方向与主文一致，具体天数仍以评估后的配置为准。

### 2.10 DEC10 认证路径

**主文原建议（§5.1、§16.5、§19）：** P0 有两条需要核实的候选路径：取得合法授权的核验服务；在允许用途与流程确认后，由受控审核人员通过官方方式进行人工核验。人工路径仍必须解决本人绑定、数据保护和处理产能。两者都无法形成可靠闭环时，正式学生社区不得上线。不能假定存在任意商业 App 可直接免费调用的学籍接口。学信网用户协议限制未授权的第三方工具和自动化操作。用户授权提供资料，不等同于已经取得对官方服务进行自动化调用的授权（[R04]）。不采集学信网账号密码，不在 App 内模拟官方登录，不把 OCR、邮箱后缀、姓名相同或验证码首次使用作为单独通过依据。

主文对掌上大学的公开资料判断是：隐私条款说明社区学生核验，但**未明确等于学信网接口**（[R05][R06]）。启动包要求 DEC10 在 PC01 通过及正式认证实现承诺前决定，且不能留到原型冻结之后。

**本次决定（探路顺序）：** 认证方式上，先了解掌上大学使用什么 API 做学信网认证；若无法证实，就先走代理，可使用第三方 API 进行相关认证；都不可用，再用人工审核认证材料兜底。必须能学信网认证。

**必须同时记录的限制：**

- 这是**调查与接入的先后顺序**，不是已经选定的供应商，也不是对任一第三方或人工方式「天然足够」的承诺。
- 用户说的「代理 / 第三方 API」，**不得理解为授权抓取、绕过官方登录、在 App 内模拟学信网，或使用未许可的自动化工具**。这类做法与主文 §5.1 和 [R04] 冲突，本文明确排除。
- 允许用途与授权合法性、申请人与学籍主体的对应真实性、以及学籍有效状态，**仍待验证**（PC01）。验证未完成前，不能把路径写成已可上线。
- 人工审核材料是兜底，不是降低标准。人工同样要分别核验报告有效性、本人一致、学籍状态和学校匹配；不能用学生证 OCR、邮箱或姓名相同单独放行。人工产能、材料隔离和到期删除仍要单独设计（§5.5、§5.6）。
- 四项条件不能闭环时，正式学生社区不得上线。不能为了提高转化率取消学信网核验（§13.5）。

**分层状态：** 探路顺序属于产品方向已确认；路径可用性、合法性与本人绑定属于可行性 / 准入证据未完成。认证页在证据出来前只能停在示意，不能把人脸、身份证或学信网密码画成最终方案（01 文档第 6 节）。

**2026-11-17 追加澄清（不覆盖 11-16 探路顺序）：**

- 认证目标调整为：可信确认「当前用户是否为某校学生」。**不必取得完整学籍报告**，也不把「未返回完整学籍字段」直接判为路径不可用。
- 在掌上大学路径没有公开接口证据时，可以使用微信开放平台或支付宝的学生认证，并希望复用其资格结果。这些产品公开文档多写用于学生优惠，校园社区用途是否获准属于**待申请**，不能因用途尚未证实就直接断言禁止，也不能写成已经获准。
- 「是否学生」与「是哪一所学校的学生」必须分开：若第三方只返回学生身份布尔、不返回学校且不能核验用户提交的学校，则只能记录学生身份，**不能据此放行本校成员权和本校默认可见**。用户自填学校不能当作可信归属。要放行本校，须另有可信的学校匹配证据（见 04 文档）。
- 不得自行增加身份证号或人脸作为默认必采字段。第三方核验组件若在其流程内采集，属于该平台的流程，校哩默认表单不主动加这些字段。
- 本澄清**不**把资格扩大到所有历史毕业生、结业或肄业自动有权。微信公开覆盖写的是普通高等学校在读大学生；其他状态仍按 DEC02 待细化白名单处理。
- 11-16 关于禁止未许可抓取、不承诺路径天然足够、PC01 未完成前不能写成已可上线的限制，全部保留。人工兜底仍可保留，但不再把「必须上传完整报告」写成唯一合格材料。

**2026-11-17 追加备用路径（不覆盖此前探路顺序与同日澄清）：**

- 若没有稳定接口，采用用户确认的备用方案：开发微信学生认证小程序；用户在已登录的校哩 App 中取得一张短时二维码（小程序码），用微信扫码打开该小程序完成学生认证，通过后更新原校哩账号的学生认证标记。
- **状态：用户确认的备用产品路径，未实施；平台能力及用途待验证。** 本文不再讨论是否采用。流程、抢绑保护、失效重试与确认绑定的设计见 04 文档第 3.1 节；会话 TTL、隔离与最小审计见 05 文档。
- 「保留二维码」不是永久有效：码和会话短时失效，失效后可在已登录 App 内重新生成。同手机从相册识别进入小程序能否完成全流程，待真机验证，不声称已实测。
- 不同用户认领时，不得在首次扫描即更新原账号；须有明确的绑定确认和扫码抢绑保护。同一微信身份与校哩账号的关联数量策略待定，本文不代为规定。
- 绑定依靠服务端原始认证会话加上相关用户确认。openid / UnionID 不可直接跨 App 与小程序混用；不默认 UnionID 可得。
- 学生标记与学校归属仍然分离：未验证学校不得获得本校权限。平台用途与准入限制不因改为小程序中转而消失；官方查询接口稳定性仍是依赖，不能说完全绕开接口。人工兜底保留，不新增身份证或人脸为默认必采字段。

## 4. 仍需用户选择或补证据的重大项

下面这些不会在本文里代为决定。后续认证与技术研究（04、05）可以提供选项和证据，但不能代替选择。

1. **未成年人保护怎么做够再开放。** 不限年龄已定，但分层档位、私信加严、适龄内容、监护与投诉机制、以及核验回执给不出可靠年龄时怎么办，都还没有方案。
2. **哪些学籍状态授予社区权。** 尤其：休学、保留学籍、退学、未知、已毕业 / 结业 / 肄业、自考、录取未注册。需要一张可执行的白名单，而不能停留在「都可支持」。
3. **认证接入的合法可用路径与学校字段。** 扫码打开认证小程序已确认为备用产品路径，但仍未实施。待补的是证据而不是是否采用：学生验证用途与类目能否获准、官方接口是否稳定可用、相册识别与小程序码生成的真机表现、同一微信身份与校哩账号的关联策略。微信公开接口仍不返回学校；未验证学校不得放行本校。详见 04 文档 V0.3。
4. **四川试点的具体学校、负责人和预算。** 代码不限制两校，但第一批开哪些校、封闭试点名单如何维护、无收入跑道能支撑多久，仍要回填。
5. **一年复核如何与更短的报告有效期、风险触发、毕业收权一起配置。** 以及各类数据（认证材料、资格凭据、私信、备份等）的保留和删除期限，评估完成前不冻结。
6. **一人路线下，设计、QA、认证审核和校园运营的外部支持是否落实。** 不落实会直接限制人工兜底和双校治理是否可运转。
7. **技术栈已在第 6 节 TECH 记录，不再作为「是否采用」的开放问题。** 仍待选择或补证据的是：管理后台在 Vue3 与 React 中二选一（Vue3 仅为建议）；自建库的大版本 / 插件兼容与中文检索 PoC；主机拓扑（单机起步只是建议，用户未拍板）；云产品规格与预算；RPO / RTO 与分类保留天数是否采用评估起点。认证方案仍见 04 文档 V0.3，不在此重开。
