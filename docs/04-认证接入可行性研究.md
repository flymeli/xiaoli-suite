# 校哩认证接入可行性研究

- 版本：研究稿 V0.3
- 日期：2026年11月16日（Asia/Shanghai）
- 修订：2026-11-17 二次追加。录入用户确认的备用产品路径（已登录 App 申请认证会话，短时一次性凭证生成小程序码，微信扫码认证后更新原账号学生标记）。该路径**未实施**，平台能力及用途**待验证**。旧结论不删除，见第 9 节修订日志。同日稍早的 V0.2 门槛纠偏仍然有效。
- 访问日期：学信网与掌上大学条目以 2026-11-16 为准；微信、支付宝开发者文档以 2026-11-17（Asia/Shanghai）复核为准，文中逐条标明。
- 用途：核对「当前用户是否为某校学生」能否被可信确认。不必取得完整学籍报告。本文不是已获准接入，也不是采购或上线承诺。
- 方法：只查公开官方文档与条款。未注册、未提交申请、未填写表单、未联系供应商、未购买。无公开接口证据即写「未知」。页面抓取失败不写成产品不存在。用途尚未获准，不直接断言禁止。
- 约束：不把抓取、模拟官方登录或未许可自动化当作「代理」。不把芝麻学历、支付宝自有学生优惠，或阿里云账号学生验证，当作面向第三方的开放查询 API。不得自行增加身份证或人脸为默认必采字段。用户自填学校不能当作可信归属。

## 1. 2026-11-17 目标与门槛（纠偏）

用户当日澄清：不必取得完整学籍报告；目标只是可信确认「当前用户是否为某校学生」。掌上大学路径若无公开接口证据，可以使用微信开发平台或支付宝的学生认证，并希望复用其资格结果。这些产品公开用途多为学生优惠，校哩希望用于校园社区资格。

必须拆开的两层结果，不可混用：

| 结果层 | 含义 | 能否单独放行本校（默认仅本校可见、本校成员权） |
|---|---|---|
| 学生身份 | 可信确认「当前绑定账号的本人是学生」 | 不能。最多支撑「已认证学生」类资格（例如全站已认证学生可见），且仍取决于用途获准与覆盖范围 |
| 学校归属 | 可信确认「该学生属于某一所已开通学校」 | 需要学校名称 / 标识的官方返回，或官方接口对用户提交学校的匹配核验，或其它同等可信的学校匹配证据 |

V0.1 把「未返回完整学籍字段」直接写成路径不可用，门槛过严，现予解除。纠偏后的规则是：

- 没有学校字段、也不能核验用户提交学校时，该路径**只能认证学生身份，不能放行本校**。
- 可以与其它**可信**学校匹配证据组合后，再放行本校。
- **不能**把用户自填学校当作可信学校结果。
- 不把毕业、结业、肄业等历史状态自动扩成在校权利（与 DEC02 一致）。
- 不把身份证、人脸加进校哩默认必采字段。

证据状态约定：

| 标记 | 含义 |
|---|---|
| 已核实 | 官方公开文档已写明，且本次已打开或可由检索结果稳定引用该文档正文 |
| 待申请 | 能力或产品在文档中存在，但开通、类目、用途或形态是否获准，必须由主体申请后才能确定 |
| 未知 | 本次未找到可核验的公开接口说明或字段；不是「产品不存在」 |

## 3. 推荐路径（在证据范围内）

1. **先按「结果是否够用」而不是「报告是否完整」来选型。** 若只要「是否学生」，微信公开接口在开通获准后，可以提供与该小程序 openid 绑定的学生身份布尔。这是本次唯一已核实、字段写清的开发者查询接口。支付宝仍缺同等公开字段，保持跟进，不承诺、不排除。
2. **学校字段缺失时的产品后果。** 仅凭微信 `is_student`，可以设计「已认证学生」状态，**不能**据此把用户写入某所学校或打开仅本校能力。可见性若默认仅本校，则该用户仍应被视为学校未确认，不能进入本校信息流、本校成员身份或学校主数据。全站已认证学生可见（ALL_VERIFIED）是否对「学校未确认、仅学生身份已确认」的用户开放，属于产品选择，须另做决定；即便开放，也不得把自填学校展示成已核验归属。
3. **要放行本校，必须追加可信的学校匹配证据**，例如：供应商后续在正式文档中返回学校名称 / id 并与校哩学校主数据匹配；或官方接口接受用户提交的学校并返回匹配结果；或受控人工路径核验官方报告中的学校（此时报告是证据来源之一，不是默认人人必传）。在得到这类证据前，不要上线「本校社区」的正式放行。
4. **支付宝不要误用现成接口。** 不要调用已取消的 `is_student_certified`；不要把校园付学校名录查询、K12 / 校园刷脸代扣、芝麻学历展示或支付宝自己的学生优惠，当作开放的「是否某校学生」查询 API。`zhima.customer.jobworth.authentication.query` 公开 `identity_type` 目前只写明 `04` 教师，其它类型须联系芝麻支持确认——本研究不联系，故学生类型是否存在记为未知。
5. **形态上不要假定 App 已接通。** 若走微信路径，首期更可能是：符合条件的境内非个人主体小程序申请「学生验证」，用户在小程序内完成插件授权，服务端持 openid 与授权码查询，再把结果绑到校哩账号。独立 App 经小程序中转属待申请，须在获准前把认证页保持示意。
6. **人工兜底可保留，但不再是「必须上传完整报告」的默认流程。** 也不把身份证、人脸设为校哩默认必采。若审核人员经官方渠道核验，仍须分别确认本人一致、在读或白名单状态、以及学校匹配，且不得使用学信网账号密码或模拟登录。
7. **用途与类目获准前，路径只是候选。** 微信文档的优惠用途是已核实的申请条件，不是校哩已经通过或已被拒绝的证明。申请结果出来前，不能宣传「已接入官方学生认证」，也不能把正式学生社区的上线时间写成已确定。
8. **覆盖缺口要写进资格规则，不要口头放宽。** 微信公开范围是普通高校在读专科到博士、且限大陆二代身份证。未成年人保护仍按 DEC01 单独做；毕业后再查可能变为非学生，须设计重新授权 / 资格回收，不能把一次 `is_student = true` 写成永久在校。
9. **无稳定直连时，采用用户已确认的备用产品路径（见 3.1）。** 这是备用方案，不是已经上线的实现，也不能写成已经绕开官方接口或用途准入。

## 3.1 备用产品路径：已登录 App 扫码至认证小程序（2026-11-17）

**状态：用户确认的备用产品路径，未实施；平台能力及用途待验证。** 本文把它写入产品探路，不再讨论是否采用。它不替代 11-16 的调查顺序，也不把人工兜底取消。下面流程是设计建议，须与已核实证据分开阅读。

### 设计建议流程

1. **已登录 App 申请服务端认证会话。** 用户须先持有有效的校哩登录态。App 向服务端申请创建一个认证会话。会话在服务端绑定该校哩账号、创建时间、短时失效时间和状态（已创建 / 已扫码待确认 / 已完成 / 已取消 / 已过期等）。
2. **短时、一次性、不透明随机凭证，用于生成小程序码。** 服务端为该会话签发一枚高熵、不可猜测的不透明随机凭证，只用于把扫码入口关联到会话。凭证**不得**编码或嵌入姓名、手机号、证件号、学校、校哩账号 ID、openid 或其他永久用户标识。展示给用户的是小程序码（或等价二维码），不是把该凭证当可复制口令对外输出。具体使用微信哪一种码、场景值长度与生成接口限制，实施前按当时官方文档复核，本次不新做大范围核验。
3. **「保留二维码」不是永久有效。** 凭证与码均短时失效；过期、取消或已完成后立即作废。用户可在仍登录的 App 内重新申请，生成新的会话和码。不得把同一张码做成长期入口。
4. **微信扫码打开认证小程序，走官方登录与用户授权。** 用户使用微信扫描该码，进入校哩认证小程序，完成微信官方登录，并按官方学生验证流程授权。同手机将码存入相册再识别进入小程序，能否走完整流程，**待真机验证**；本文未实测，不作承诺。
5. **后台只用平台官方查询结果做核验。** 小程序服务端按已核实的官方接口查询，以 `bind_status = 3` 且 `is_student = true` 作为学生身份通过条件（审核中或失败不得放行）。此步仍依赖官方接口的可用性、配额和开通结果。**小程序中转不会让平台用途 / 准入限制消失，也不能说完全绕开接口。** 官方接口稳定性仍是依赖。
6. **不得在首次扫描时更新原账号。** 官方查询通过后，仍须由当前微信侧用户**明确确认**：把本次认证结果绑定到该认证会话所对应的原校哩账号。服务端此时只展示会话的最小必要信息（例如脱敏昵称或申请时间），不得回显完整账号标识或原始凭证。不同微信用户扫到他人的码时，视为认领冲突：应提示这是他人发起的会话，提供取消或拒绝，**首次扫描不得把原账号改成已认证**。同一微信身份可关联多少个校哩账号、一个校哩账号可绑定多少微信身份，**策略待定**，本文不预设。
7. **服务端原子完成，防重放、幂等。** 用户确认后，服务端在同一事务内校验：会话未过期、未取消、凭证一次性且未消费、状态允许完成、官方查询结果仍有效。然后只更新「学生标记」（与学校归属分离，见下），作废凭证，写入最小审计。重复提交、重放已消费凭证或并发确认，不得造成第二次状态跃迁。用户可主动取消；过期或失败后应允许在 App 内重试（生成新会话，不复用旧凭证）。
8. **扫码抢绑保护。** 须防止他人先扫先占：会话在「已扫码待确认」期间应锁定当前微信身份与原会话的对应关系，或要求发起方在 App 内再次确认后再完成。绑定依据是**服务端原始认证会话，加上相关用户的明确确认**，而不是把 App 的 openid 与小程序 openid 直接混用。openid 按应用隔离，不可直接跨 App 与小程序互换。UnionID 仅在同一开放平台主体且官方条件满足时才可能得到，**不默认可得，也不作为本路径的前提。**
9. **App 只从校哩服务端获取更新。** 认证完成后，App 通过查询自有服务端（下次打开、受控轮询或校哩自有推送——属设计建议）读取会话状态与学生标记。**不要依赖微信平台一定会向 App 推送完成回调。** 平台侧是查询还是回调，以官方当时是否支持为准：已核实的是服务端查询接口；面向 App 的完成回调本次没有当作已核实能力。须区分设计建议与证据。

### 必须同时成立的限制

- **学生标记与学校归属分离。** 本路径在官方接口仍不返回学校、也不能核验用户提交学校时，只能更新「学生身份已确认」。未验证学校不得获得本校成员权、本校默认可见或写入学校主数据。用户自填学校仍不能当作可信归属。这与 DEC07（默认仅本校，可选全站已认证学生）直接相关；「学校未确认的已认证学生」能否进入全站已认证可见，仍待产品决定。
- **人工兜底保留。** 官方查询失败、覆盖范围外、或需要学校匹配证据时，仍可走人工路径。不新增身份证或人脸为默认必采字段。
- **未实施，不得对外宣传已接入。** 小程序主体、类目、学生验证开通、码的生成与扫码体验、相册识别，均待申请或真机验证。PC01 完成前，认证页保持示意。

## 4. 学信网公开能力（2026-11-16，背景仍有效）

学信网仍是国内学籍学历核验的权威来源，但校哩**不必自己持有完整报告副本**才能完成第 1 节的目标。下列事实继续作为背景，避免把第三方结果误写成学信网官方接口。

- 学籍信息查询范围包括国内高等教育的各类高等教育学历教育身份信息，包含学籍档案已经离开学校的，不含自学考试（《查询范围与结果说明》，<https://www.chsi.com.cn/help/cxfw.jsp>）。
- 「在校生学籍审核」查询范围不含自学考试；可查询学籍档案已离开学校（如毕业、结业、肄业、退学、取消学籍等）的相应学籍信息（同页）。
- 学历查询对象为国民教育系列高等教育学历证书及相关信息（同页）。
- 「如何在线申请授权」说明：学信网为机构用户提供授权服务，机构登录后才能办理授权；未注册机构用户须先注册（<https://www.chsi.com.cn/help/rhsq.jsp>）。**本次未注册，能否批给校哩、批什么用途，未知。**
- 「院校专用申请渠道」列出专用申请凭证、批量在线验证、注册信息核对、学历学位认证、图像校对等，对象写的是高等院校和省级教育管理部门（<https://www.chsi.com.cn/help/yzzw.jsp>）。
- 「报告有效期」：中文报告首次申请有效期最长 180 天，英文最长 180 天；申请成功后 30 天内可调整延长（<https://www.chsi.com.cn/help/bgys.jsp>）。已过期报告不会展示申请时的内容。
- 2025-04-18 学信网声明：一些非官方渠道打着学信网旗号招揽代办，存在信息和财产风险，甚至没有真正申请报告（《声明》，<https://kl.chsi.com.cn/wap/help/ckjjfa.action?id=dljzinycvhglkwku>）。
- 用户服务协议关于未许可第三方与自动化的限制，官网存在协议页；本次未完整取到协议正文，涉及可执行限制处标未完整取证。官方授权代理机构指各省（区、市）教育行政部门指定的申请受理机构，**不是**任意第三方商业接口。

## 5. 掌上大学（2026-11-16，结论未变）

公开可见的《掌上大学及关联产品隐私政策》更新时间为 2025-08-11，访问 2026-11-16：<https://res-page.zsdx.cn/app/agreement/privacy.html>。该文写明：学生认证信息用于在用户「明示授权同意」后，通过国家权威可信身份认证机构核验身份，并按认证结果提供社区服务或限制；认证信息包括学校、院系、入学时间、学制、姓名、入学时间。

**本文仍不能把它写成掌上大学的开放 API 说明书。** 页面没有给出接口名称、申请入口、返回字段、允许用途、价格或留存要求。因此「掌上大学实际用什么接口、能否向校哩开放、能否返回学校并供本校放行」继续为**未知**。按 11-16 探路顺序，这条路径在补证前不能作为已选定供应商。

## 7. 支付宝：已排除项与仍为未知的项（2026-11-17）

访问日期均为 2026-11-17。目标是寻找**面向开发者**的学生 / 校园身份认证查询接口和正式产品说明。

**已核实、但不是本目标的接口或说明：**

- 会员授权查询字段 `is_student_certified`：支付宝开放平台客服 FAQ（2020-11-17）写明，2019-12-24 之后上线的应用调用 `alipay.user.info.share` 将不再返回该字段。<https://opensupport.alipay.com/support/FAQ/c9ace687-b547-4738-9f34-ba52c5912b45>
- `alipay.commerce.educate.campus.institutions.query`：查询校园付场景下的学校机构信息，不是「当前用户是否为某校学生」。<https://opendocs.alipay.com/open/037i8f>
- 校园支付、K12 代扣或刷脸类教育支付接口：属于支付与校园场景产品。部分流程可能涉及人脸或证件，**不得**因此把身份证或人脸设为校哩默认必采，也不得把它们当成通用学生身份查询 API。

**官方存在、但公开枚举尚未覆盖学生查询的接口：**

- `zhima.customer.jobworth.authentication.query`（文档显示更新 2026-08-26）：<https://opendocs.alipay.com/open/351177b5_zhima.customer.jobworth.authentication.query>。公开文档将 `identity_type` 列为 `04`（教师），并写其它身份类型须联系芝麻技术支持确认。本次**不联系**。一次整页抓取超时，故响应字段全集以该文档的公开目录与检索摘录为准，未把超时写成接口不存在。
- 芝麻身份信息验证接入准备：<https://opendocs.alipay.com/open/05bgep>。说明需创建应用、开通产品；提到可创建小程序或网页 / 移动应用。这是身份验真类产品的开通说明，不能直接等同于「已开放学生身份查询」。
- 产品介绍页 <https://opendocs.alipay.com/open/20170906150025920611/ye8gld> 本次抓取未取得正文。**不据此断言产品不存在。**

**明确不采用的口径：** 芝麻学历展示、支付宝站内学生优惠、非官方站点上的「学生验证」样例，均不作为开放 API 证据。

结论：支付宝是否向开发者提供「查询当前用户是否学生、是否某校、或匹配用户提交学校」的正式接口，**仍为未知**。跟进方式只能是继续核对开放平台产品目录与接口字段，而不是把相邻产品拼成已可用路径。

## 8. 对 DEC10、原型和 05 文档的直接含义

- 11-16 的探路顺序保留：先证实掌上大学，再看第三方，再人工兜底。11-17 把微信、支付宝明确列为可调查、可复用资格结果的第三方候选，并把「完整报告」从必须门槛中拿掉。
- 合法性、允许用途、开通申请结果（PC01）仍未完成。没有获准前，认证页保持示意，不画学信网密码，也不把人脸或身份证画成最终默认方案。
- 若首期只能拿到学生布尔：产品须增加「学生身份已确认、学校未确认」的状态，避免把未匹配学校的用户放进本校。这与 **DEC07**「默认仅本校、可选全站已认证学生」直接相关，需要后续产品决定，本文不擅自改规格。（V0.2 曾误写为 DEC05，DEC05 是首期商业化，现予更正。）
- 技术侧：资格结果、openid / 小程序用户标识、授权时间、认证会话与短时凭证摘要应记在服务端，并按 05 文档做 TTL、隔离和最小审计。没有材料时不必默认开辟「报告副本」存储；一旦有人工材料，仍须隔离。详见 05 文档 V0.3。
- 11-17 晚些时候确认的扫码小程序备用路径已写入第 3.1 节：用户确认采用为备用方案，但未实施，平台能力及用途待验证。它不能写成已绕开官方接口或用途限制。
