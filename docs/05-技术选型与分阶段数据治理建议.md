## 1. 已确认技术栈

在一人加 AI、先做双端社区和受控私信的前提下，采用已确认的「小而完整」一套。若认证路径只保存第三方资格结果，不必默认采集或上传完整学籍报告、身份证或人脸；只有确实收到认证材料时，才必须与普通媒体隔离存放。备用扫码路径（04 文档 V0.3 第 3.1 节，未实施，平台能力及用途待验证）若启用，认证会话与短时一次性凭证属于资格凭据，应放在主库受控表中，设定短 TTL，并做最小审计；不要写入内容桶或日志明文。

**历史备选（不再并列待选）：** 此前建议稿把「托管 PostgreSQL」作为默认、MySQL 作为可接受并列候选，并讨论过 MongoDB。现仅作对照：MySQL 仍可在退出或迁移场景评估；MongoDB **不建议作为资格和权限的主库**。不要把情侣项目若曾排除 MySQL 当作额外约束。

不推荐作为早期组合的做法：以 MongoDB 同时承担资格权限和全文搜索；一开始就上 Elasticsearch / OpenSearch 集群；内容桶设为公共读；用长期有效签名或未鉴权 CDN 地址分发原图；把认证材料与作品媒体放在同一可被 CDN 分发的空间；把数据库 5432 对公网开放；用 `latest` 或来源不清的第三方预构建镜像作为生产数据库。

## 3. 历史对照：PostgreSQL / MySQL / MongoDB

本节保留 2026-11-16 的能力对照，便于理解为何最终确认 PostgreSQL，**不再表示这三项仍待用户选择**。当时建议「默认托管 PostgreSQL」已被 TECH01 取代。

资格、学校成员、可见范围、私信请求都是强一致关系数据，适合事务型关系数据库。Postgres 在约束、JSONB（草稿与审计）以及官方 PITR（基础备份 + WAL 持续归档）方面有完整手册说明。MySQL 同样是事务型关系数据库，官方也支持备份与二进制日志的时间点恢复；其 ngram 全文解析器面向中日韩，但是自建中文分词插件生态与本次「用 PG 插件」的已确认方向不同。MongoDB 文档灵活，适合变化快的内容形态，但学校主数据、资格状态机和可见范围更适合规范化表，不建议作为资格和权限的权威库。

性能数字（如某云「P95 多少毫秒」）没有在指定数据规模下的两个独立测试来源，**全部标为未验证**，不以主文 §15.4 的建议目标冒充已达到的指标。

## 4. 自建 Docker 上的中文全文检索（合理路径，待 PoC）

需求来自主文：搜索不能成为权限旁路（§6.4、AT09）；删除、下架、拉黑、资格失效后，索引和缓存须一起失效；首期不要热搜榜。用户已确认前期用 PostgreSQL 插件支持全文检索，且自建须能支持中文。

本次只查公开官方与上游文档，**未编译、未建容器、未跑查询**。凡涉及「能否在选定大版本上装上、分词是否可接受、升级后索引是否仍可用」，一律标 **待 PoC**。完整的「PG 大版本 × 插件版本 × SCWS 版本 × 基础镜像 digest」矩阵，公开材料不足以写成已验证结论，**标未验证，不编造当前补丁版本**。

### 4.1 官方能力边界（已核实文档，2026-11-17）

- PostgreSQL 内置全文检索面向已分词的词项；`pg_trgm` 官方说明是对 **alphanumeric** 文本做三元组相似匹配，并且「提取三元组时忽略非单词字符（non-alphanumerics）」（<https://www.postgresql.org/docs/current/pgtrgm.html>，访问时手册对应 Documentation 18）。因此，默认构建下，连续中文往往不会被当成可提取的单词三元组。官方把 `pg_trgm` 与全文索引结合的拼写建议，建立在已经切出的词表之上，**不能**把它当作连续中文的完整分词器，也**不能**把它当作中文拼写纠错的保证。它仍可用于已经切出的拉丁片段、部分相似匹配或 `LIKE` 加速，但是只是补充。
- 中文分词需要额外解析器。上游常见候选是 [zhparser](https://github.com/amutu/zhparser)（基于 SCWS）。其 README（2026-11-17 读取）写明：支持 PostgreSQL 9.2 及以上；安装须先编译 [SCWS](https://github.com/hightman/scws)，文档示例获取的是 `scws-1.2.3`；再编译安装 zhparser，以 `CREATE EXTENSION zhparser` 后自建文本搜索配置（`PARSER = zhparser`）并做词性映射。自定义词库与 `sync_zhprs_custom_word()` 也在该 README 中说明。
- SCWS 官方站点 <https://www.xunsearch.com/scws/>（2026-11-17）仍将引擎介绍为基于词频词典的机械分词，BSD 许可，源码托管 GitHub。站点「动态」栏最近一条正式发布说明是 **2016-02-24：SCWS-1.2.3**。这意味着自建路径依赖一套发布间隔很长的分词引擎，能否在目标操作系统与选定 PG 大版本上干净编译、词典如何维护，**待 PoC**，不能写成已经无风险。
- 腾讯云数据库 PostgreSQL 的 zhparser 文档（<https://cloud.tencent.com/document/product/409/138228>，2026-11-17 再核）列出的是**托管内核**适配版本（文中按 PG 10–18 给出对应 `v*_r*` 门槛，并要求用 `SHOW tencentdb_version;` 查看）。这只能证明该托管产品提供了插件，**不能**等同为官方上游在自建 Docker 中已经支持同一版本矩阵，也不能直接拿来锁定自建镜像。

### 4.2 建议的自建方式（设计建议，不是已经建成）

1. **先锁定 PostgreSQL 大版本，再谈插件。** 以当时 PostgreSQL 官方社区版本与安全公告为准，选定一个大版本后，在该版本上做 PoC。访问当日手册路径 `/docs/current/` 解析到 18 卷，这只说明文档版次，**不是**已经为校哩锁定 18.x 的某一补丁号。
2. **基础镜像只用来自可复核来源的官方镜像，并固定 digest。** 建议以 Docker Official Image 的 `postgres` 一类官方镜像为起点，写入完整镜像 digest，而不是标签 `latest`，也不把标签浮动当成版本冻结。
3. **插件在自有、可重建的镜像里编译。** Dockerfile 与构建脚本纳入版本库：固定 OS 包来源、固定 SCWS 与 zhparser 的源码 commit（或发布 tarball 的校验和）、固定词典文件来源与校验和。构建产物可重复得到同一 digest。zhparser README 中的「Docker 快速体验」镜像（如 `zhparser/zhparser:bookworm-16`）只是上游提供的体验入口，**生产不得把来源与 digest 未审核的第三方预构建镜像当作依据**，即使它声称基于官方 Postgres 镜像。
4. **PoC 最低验收（未做，须补）：** 在锁定的大版本镜像中成功 `CREATE EXTENSION zhparser`（或经评估后改用其它上游中文解析器，须同样固定 commit 并重做本节约束）；对校园场景样例（学校名、课程、口语与连续中文）检查分词；自定义词生效；带权限条件的 GIN 查询；容器销毁后数据卷仍在但**不能**把这一点当成备份已成功；模拟小版本与一次大版本升级演练。分词质量、召回与错别字能力相对独立引擎的差距，**未实测，标未验证**。
5. **权限与删除规则不变：** 可见范围与资格条件必须在同一条查询里完成，禁止先搜后过滤的宽查。删帖 / 撤权与数据库状态同一事务更新。若将来按第 8 节拆出独立引擎，仍以主库权限为准，索引只是加速，并须证明已删内容不会从索引或备份中重新可搜。
6. **升级、词典与回滚。** 官方 `pg_upgrade` 说明：外部模块必须与新服务端二进制兼容，但 **pg_upgrade 不能替你检查这一点**；新集群必须预先安装与新版本匹配的扩展共享库，且不要再执行会重复定义的 `CREATE EXTENSION`；升级后可能需要按工具生成的脚本重建表或索引（<https://www.postgresql.org/docs/current/pgupgrade.html>，2026-11-17）。自建时还须保证 SCWS / zhparser 词典与自定义词库在新镜像中路径一致、升级后重建文本搜索索引，并保留旧集群直到新集群通过只读校验。使用 link 模式会与旧数据目录产生关联，官方建议在需要保留可回滚副本时改用 clone 或先复制再升级。升级与回滚步骤必须在隔离环境演练，不能只在生产上第一次做。

**增长期触发后再评估独立引擎：** 见第 8 节。评估顺序建议：先轻量引擎，再考虑 Elasticsearch / OpenSearch 集群。后者运维和费用更高，一人路线不应作为默认第一步。任何引擎都要核验：中文分词、过滤安全性、删除 API、备份与重建时间。Meilisearch 等只作成对照，**不等于已经选定**。

## 5. 图视频、对象存储与认证材料隔离

原则：文件和元数据分离。数据库保存作品 ID、对象键、校验和、内容类型、可见范围、审核与处理状态、过期时间；对象存储只保存字节。应用永远不要把可长期匿名访问的原图或原片 URL 写进 Feed。认证小程序备用路径与材料按需隔离的规则保持不变。

**桶与权限：**

- `verify` 桶：仅在确实采集到认证材料时启用（例如人工兜底的文件或审核工作副本）。关闭公开访问和 CDN。仅审核角色经短时签名、带审计地打开。生命周期按「终局后短期删除」配置，删除清单必须进入备份抑制（见第 6、7 节）。若认证只使用微信 / 支付宝等资格结果，默认不在此桶存放完整学籍报告，也不把身份证或人脸作为默认必采文件。
- `media` 桶：私有读写。上传用短时上传签名或服务端中转；下载 / 播放用短时签名，建议与主文 §15.3 一致，把已签发地址的残余窗口作为验收项（建议不超过 60 秒，需实测，不是已承诺 SLA）。
- 拉黑、下架、范围收窄后，服务端停止签发新地址，并接受「旧签名在过期前可能仍能打开」的上限；若要求零残余，需改用可撤销签名或再鉴权，成本与复杂度另估。

**CDN、防盗刷与流量计费（避免重复相加）：**

- 腾讯云 COS 官方文档说明：存储桶默认私有读，可用预签名 URL 做限时上传下载；并提醒控制签名有效期，慎用永久密钥（<https://cloud.tencent.com/document/product/436/68284>，2026-11-16）。
- 面向播放的分发，应使用 CDN 自己的鉴权（如 TypeA 时间戳签名，官方说明签名错误或过期返回 403，<https://cloud.tencent.com/document/product/228/41623>），并配合 Referer 防盗链（防盗链不能单独当作权限系统）。**不要把对象存储预签名参数直接套到未核验的 CDN 域名上**；二者是否可混用，须按当时文档复核，未核实前按「源站签名与 CDN 鉴权分开配置」处理。
- 官方把「用户直连 COS 下载」和「经 CDN 加速下载」分成不同计费项。直连对象链接或源站浏览计入 COS **外网下行流量**；将 COS 作为 CDN 源站时，客户端从节点下载计入 **CDN 下行流量**，仅当回源时另计 COS **CDN / EdgeOne 回源流量** 和 COS 请求费（<https://cloud.tencent.com/document/product/436/53863>，文内更新 2026-08-26，2026-11-17 访问；<https://cloud.tencent.com/document/product/228/37849>，文内更新 2024-08-22，2026-11-17 访问）。估算媒体成本时：走 CDN 的播放不要再按同一批流量叠加一笔「COS 外网下行」；只有缓存未命中才加回源。反之，若同时把 COS 公网直链和 CDN 域名都暴露给客户端，两条路径的费用可能被一起收。全球加速等组合在官方说明中也可能同时产生多项流量，须按实际开启的功能逐项列，而不是把单价加总后当成一句报价。具体规格与预算仍未定，本文不抄示例单价。
- 防盗刷还要：按桶和路径限速、告警、异常流量可关 CDN、热门对象与认证材料隔离。这些是运营措施，不是一次配置永久有效。

**转码成本：** 按「分钟数或 GB × 清晰度条数 × 单价」参数化。具体转码产品与单价本次未用两份独立官方价目交叉写成数字，标未验证。早期建议少档（例如仅一档适合手机的转码 + 原片归档策略），避免默认为每个视频生成多档长时间保存。

## 6. 自建库的备份、安全、隔离与恢复演练（建议，非拓扑拍板）

主文 §15.4 的建议验收目标是：关键业务 RPO 不超过 1 小时，RTO 不超过 4 小时，并且要用隔离环境做真实恢复演练。本文把它视为**待验证的建议值**，不是承诺，也不是已经达到的能力。RPO / RTO **必须通过恢复演练实测**后才能写进验收，不能用建议值冒充用户已同意或已经可达。

### 6.1 持久化不是备份

- Docker 官方文档把 volume 定义为容器之外的持久化存储：容器删除后，卷里的数据仍在；备份 / 恢复是另外一套把卷内容归档到别处的操作。未使用的卷还可以被 `docker volume prune` 删掉（<https://docs.docker.com/engine/storage/volumes/>，2026-11-17）。因此，**Docker volume 只是让数据库文件在容器重建后还在，不是备份**。
- 腾讯云数据盘（或把 PGDATA 放到数据盘再挂进容器）同样只是运行中的主副本。盘故障、误卸载、同一可用区的主机事故或误格式化，都会直接打到这份数据上。云盘快照若要当作备份手段，必须单独设计一致性（见下）并复制到独立位置，不能把「已经挂了数据盘」说成已经有备份。
- PostgreSQL 官方《File System Level Backup》写明：在服务器运行时直接复制数据目录，通常得不到可用备份；要停库，或使用同时覆盖数据与 WAL 的一致快照，并理解恢复时会走崩溃恢复。文件级备份也只能恢复整个集群，不能只抽一张表（<https://www.postgresql.org/docs/current/backup-file.html>，2026-11-17）。推荐的在线方式是 `pg_basebackup` 配合持续 WAL 归档做 PITR（<https://www.postgresql.org/docs/current/continuous-archiving.html>、<https://www.postgresql.org/docs/current/app-pgbasebackup.html>，2026-11-17）。

### 6.2 备份体系（设计建议，工具协议待 PoC）

- **PITR：** 定期基础备份 + 持续 WAL 归档。归档与基础备份存放在**独立的 COS 桶**（与 `media` / `verify` 分开，关闭公有读），不要只写在数据库同一块数据盘上。启用加密、最小权限和生命周期，删除抑制规则与第 7 节一致。
- **备份工具与 COS 的协议兼容必须验证（待 PoC）。** `archive_command`、`pg_basebackup` 或第三方归档工具（若选用）是否按当时 COS 的 API / 兼容协议稳定写出、校验和可读回，须在隔离环境验证后再进入例行任务。未验证前不指定某一工具为已选。
- **周期逻辑备份（`pg_dump` / `pg_dumpall`）与 PITR 的用途不同。** 官方明确：逻辑转储不是文件系统级备份，**不能**作为持续归档方案的一环，也不能拿去和 WAL 一起重放（同 PITR 文档 Note）。逻辑备份的价值是：相对可导入更新的大版本、跨机器架构迁移、以及按库导出（<https://www.postgresql.org/docs/current/backup-dump.html>，2026-11-17）。两者都要，不要互相替代。
- **加密、异机或异地域存放及成本待评估。** 传输中与静态加密、备份桶跨地域复制或另一账号冷备，方向正确，但费用和恢复路径未测算，不能写成已批准。
- **告警至少覆盖：** 数据盘与 WAL 盘水位或故障、归档命令失败、基础备份失败、备份新鲜度超过阈值。没有这些告警，就等于不知道备份是否还活着。
- **单机故障不等于高可用。** 官方高可用章节讨论的是第二台服务器在主库失败后接替（<https://www.postgresql.org/docs/current/high-availability.html>，2026-11-17）。只有一台自建容器时，主机、Docker 引擎或数据盘故障就是停机。
- **主从复制不替代备份。** 复制会把误删、错误迁移等逻辑变更传到备库；要回到过去某一时刻，仍依赖基础备份 + 保留期内的 WAL，以及演练过的恢复步骤。官方把备份恢复与高可用分在不同章节，二者目的不同。

### 6.3 网络、权限与密钥

- **禁止把 5432 对公网开放。** 安全组与主机防火墙只允许同一私有网络内、最小范围的应用来源访问；管理入口走堡垒或临时隧道，不把数据库端口写到公网负载均衡。
- 应用使用最小权限角色，不得用超级用户跑业务。插件安装、词典同步等管理操作与业务账号分开。
- 数据库口令、备份密钥与 COS 密钥不写入镜像、仓库或日志。具体用腾讯云凭据管理还是受控文件，产品与流程待评估，但原则必须先成立。

### 6.4 应用与数据库的资源隔离（建议，不是已同意的拓扑）

用户确认的是「在腾讯云服务器里用 Docker 自建数据库」，**没有**确认应用与数据库必须共机，也没有确认必须上主从。

- **更稳妥的起步建议：** 应用与数据库分在不同云服务器（或至少不同主机与不同数据盘）。数据库主机只跑数据库容器及相关 sidecar（归档、导出），独占数据盘与 WAL 盘；媒体和备份不与 PGDATA 抢同一块盘。应用主机通过内网访问数据库。这样可以把「应用发布失误、流量打满 CPU、日志把盘写满」与数据库隔开。
- **单机共置仅作为成本压力下的建议选项，不能冒充用户已经同意这种拓扑。** 若短期共机，仍须用容器 CPU / 内存限制把应用与数据库隔开，数据库使用独立数据卷，5432 只绑内网，并明确接受：这台机器故障时应用和数据库会一起停，这不是 HA。何时分机、是否加只读副本，另行决定。
- 对象存储、CDN、短信仍走腾讯云，不把媒体文件默认落在数据库盘上。

## 8. 迁移触发条件

在出现以下情况之前，不主动加组件：

- **拆独立搜索：** 库内检索在约定的测试条件下无法满足可接受的延迟或相关性；或自定义词典 / 错别字成为明确产品需求且库内方案无法维护；或重建时间已影响到下架与删除的验收。触发后仍先评估轻量引擎，而不是直接上集群。
- **加缓存层：** 读多写少且数据库已是瓶颈，并且已设计「撤权后缓存立即失效」。没有失效方案就不加。
- **拆微服务：** 发布节奏或故障隔离已被单体明显拖累，且有第二人可分担值班。一人阶段默认不拆。
- **媒体独立账号或专有点播：** 流量费用或盗刷风险上升，或 PC03 证明需要更完整的版权与播放控制。
- **数据库与应用分机，或考虑高可用：** 共机已出现资源争用，或单机故障的停机时间不可接受。分机或上备库仍不替代备份。
- **从低档到中 / 高档：** 开通学校或有效学生接近第 2 节中档假设，或单人已无法在约定时间内完成备份演练和告警响应。先补人和值班，再扩架构。

## 9. 参数化成本公式（不编造单价）

以下只给出结构。`P_*` 一律从当时官方定价页或账单读取，并注明日期与地域；本次不以二手文章或文档里的示例单价代替官方价目。腾讯云 COS 按量计费公式已在官方文档给出（存储日费用 = 月单价 / 30 × 日均量，请求费按万次，流量费按 GB），须按第 5 节把直出与 CDN 路径分开，不要把同一批播放流量同时乘上「COS 外网下行」和「CDN 下行」。

- 对象存储：`C_store = Σ (容量_GB × P_存储[类型]) + 请求次数/10000 × P_请求 + 取回_GB × P_取回`
- 分发：走 CDN 时 `C_traffic ≈ CDN流量_GB × P_CDN + CDN回源_GB × P_回源`；仅当确实发生 COS 公网直下时，再加上 `外网下行_GB × P_下行`。开启全球加速等功能时按官方说明另列，不预先加总。
- 转码：`C_transcode = 视频分钟数 × 档位数 × P_转码`（或供应商按 GB 计，则改用 GB）
- 自建数据库：`C_db = P_CVM规格 × 时长 + 数据盘_GB × P_盘 + 备份所在 COS 存储与请求 + 必要的跨区或外网流量`（不再按托管实例套餐作为默认公式）
- 搜索（若已拆出）：`C_search = P_实例或托管套餐 + 文档量或请求量计费项`
- 认证：`C_verify = 成功或查询次数 × P_核验 + 人工件量 × 人均分钟成本`（任何 API 单价未取得官方且可引用的价目之前，只保留符号）
- 短信 / 推送 / 域名 / IM：各自按腾讯云当时官方计费项相加（主文 [R17] 已提示腾讯云 IM 以当时计费说明为准）

敏感性：用低 / 中 / 高三档学生数，再分别假设「人均月上传对象数」和「人均月下行 GB」为低 / 中 / 高三档，得到 9 个情景的符号结果。在填入 `P_*` 和实测用量前，不输出人民币总额，以免被当成报价。云产品具体规格与预算仍未定。

单人运维的主要隐形成本是演练、告警夜间处理、自建库升级和认证审核，应单独记人日，不要只看云账单。

## 10. 单人运维清单与退出路径

**日常（工作日）：** 错误率与 5xx、登录 / 认证失败、审核队列积压、对象存储流量突增、WAL / 归档 / 基础备份是否成功、备份新鲜度、证书与密钥过期、数据盘与 WAL 盘水位、数据库容器健康。

**每周：** 抽查一条「下架 / 拉黑 / 删帖」是否在 Feed、搜索、详情、媒体地址同时失效；抽查 `verify` 桶是否出现非审核访问；抽查 5432 未对公网开放；看账单中的下行、回源和请求异常。

**每月 / 每季：** 隔离环境恢复演练（第 6 节）；权限账号盘点；依赖清单（短信、存储、自建库、IM、核验）的退出步骤复习；基础镜像 digest、插件 commit 与官方文档是否变化。

**退出路径（每个关键依赖都要能回答）：**

- 数据库：逻辑备份 + 迁移脚本可在另一环境拉起；基础备份与 WAL 的恢复步骤有演练记录。镜像与插件可从 Dockerfile 和 pinned commit 重建。
- 对象存储：对象键清单、校验和、按前缀导出 / 批量拷贝；CDN 域名可切。
- 搜索：可从主库全量重建（包括文本搜索配置与自定义词典）。
- 认证供应商：保留报告核验与人工兜底流程，避免唯一自动路径突然中断后无法续验。备用小程序路径不改变这一条。
- 云账号：基础设施尽量代码化，密钥可轮换，避免只有控制台点击记录。

不能让开发者同时承担无备份的全天候内容审核和认证审核（主文 §16.2、02 文档 C-11）。

## 11. 最重要的风险

1. **认证合法路径尚未取证（见 04 文档 V0.3）。** 架构选得再稳，PC01 不过也不能正式放行学生社区。
2. **权限旁路。** 搜索、CDN、旧签名、推送深链、缓存只要有一处未按同一规则拒绝，就会打破可见范围。这是安全优先级最高的工程风险。
3. **认证材料、认证会话或资格凭据与备份删除不一致。** 一旦采集了材料，主库删了、备份或对象版本还在，会在恢复演练或合规检查时暴露。若只保存第三方结果或短时认证会话，同样要能作废和抑制恢复，避免过期凭证被备份复活后重放。
4. **一人运维过载，以及自建库运维被低估。** 过早引入搜索集群、微服务或复杂点播，会把时间从权限、归档告警和演练上挤走。自建并不自动比托管更省心。
5. **成本被媒体下行和转码放大。** 在单价和用量未实测前，任何「很便宜」的判断都未验证；公开读桶、过长签名，或把 COS 直出与 CDN 流量重复估算，都会扭曲判断。
6. **中文搜索预期过高，或把托管插件版本误当成自建已验证。** 库内方案的分词、错别字能力待 PoC；SCWS 上游正式发布间隔很长，是维护风险。
7. **把 volume / 数据盘当成备份，或把单机、主从当成已经有灾备。** 以及把尚未锁定的镜像 tag、补丁号写成已选。
8. **Flutter / Go / PostgreSQL 的具体版本和 SDK 冲突尚未关闭（PC07）。** 栈已确认，版本未锁定。

4. 备份新鲜度、归档失败、磁盘与 WAL 的告警能否在一人值班下被及时看到。
5. RPO / RTO 实测值；媒体签名残余窗口等建议验收值。
6. Flutter、Go 与所选 PostgreSQL 大版本的具体版本锁定（PC07 等）。
7. 认证路径仍按 04 文档 V0.3 取证，不在此重开方案选择。
